## Context

当前实现已经具备 TLS 握手、HTTP 响应、TCP 端口和 ICMP 等多维度检测能力，但在 `github.com` 首页场景中，浏览器真实访问成功还依赖更严格的应用层可用性判定。现有逻辑存在三个不足：

1. `github.com` 的 HTTPS 验证仍偏向“能完成 TLS + 得到一个非 5xx 响应”，无法充分区分“GitHub 正常首页”与“错误中间页/干扰页/不完整页面”
2. 候选 IP 获取使用“第一个成功的数据源即返回”的策略，导致候选池覆盖受单一源质量波动影响
3. `status` 仍以 TCP/延迟为主，用户难以判断当前 IP 是“端口通”还是“浏览器大概率能打开”

本次设计目标是在不引入新外部依赖、不实现浏览器自动控制的前提下，通过更贴近浏览器的应用层验证与更稳健的候选 IP 策略，显著提高 `github.com` 首页在浏览器中的可打开概率。

## Goals / Non-Goals

**Goals:**
- 对 `github.com` 候选 IP 引入浏览器导向的首页验证，避免误选仅端口可达但页面不可用的 IP
- 聚合多个数据源的候选 IP 并去重，提升候选池质量
- 过滤明显无效或不适合作为公网映射的 IP
- 让 `status`、`init`、`update` 的输出能区分“基础连通”与“浏览器可用性”
- 保持现有命令行单文件分发模式，不增加运行时依赖

**Non-Goals:**
- 不实现 Chrome/Edge/Firefox 的自动缓存清理或自动重启
- 不引入真实浏览器自动化（如 CDP、Playwright、Selenium）
- 不为所有 GitHub 相关域名做同等重量的 HTML 内容校验，仅优先强化 `github.com` 首页场景
- 不新增后台守护进程或持续健康检查服务

## Decisions

### 决策 1：将浏览器级验证聚焦在 `github.com` 首页，而非所有域名一视同仁

**选择**：仅对 `github.com` 使用更严格的首页验证；其他域名继续采用现有 HTTPS/TCP 方式。

**理由**：
- 用户最关心的是浏览器打开 `https://github.com/`
- 其他域名如 `raw.githubusercontent.com`、`api.github.com` 更偏 API/静态资源场景，不适合统一按 HTML 首页标准校验
- 这样可以把额外成本集中在最关键的域名上，避免整体检测时间明显变慢

**替代方案**：
- 对所有域名做内容特征校验：成本更高，且很多域名没有稳定 HTML 特征
- 完全不做内容层校验：无法解决“端口通、响应存在、浏览器仍打不开”的误判问题

### 决策 2：为 `github.com` 增加响应特征校验，而不仅看状态码

**选择**：在现有 TLS + HTTP GET 基础上，对 `github.com` 追加响应内容特征检查，例如响应体中是否包含稳定的 GitHub 首页关键标识、响应最终主机是否仍属于 GitHub 预期范围、页面内容长度是否达到最小阈值。

**理由**：
- 仅 `StatusCode < 500` 容易将拦截页、错误中转页、极短异常响应误判为可用
- 简单的内容特征校验可以在不引入浏览器的情况下，更接近真实首页可用性

**替代方案**：
- 使用完整 DOM 校验或无头浏览器：准确但过重，不符合本项目定位
- 仅检查响应头：对异常中间页区分能力不足

### 决策 3：将多数据源策略从 failover 改为聚合并去重

**选择**：依次拉取所有启用的数据源，把成功返回的候选 IP 合并到同一域名下，并进行去重与合法性过滤；若全部失败，再回退到内置默认列表。

**理由**：
- 浏览器可用 IP 在不同数据源间可能互补，聚合能显著扩大候选空间
- 对上游波动更鲁棒，不会因为首个成功源质量一般而提前停止

**替代方案**：
- 保持首个成功即返回：实现简单，但错过其他源的更优 IP
- 固定全部并发请求：也可行，但当前串行聚合已足够简单稳定，后续可再优化为并发

### 决策 4：加入候选 IP 合法性过滤

**选择**：在候选 IP 进入检测流程前，过滤非法 IPv4/IPv6、私网地址、环回地址、链路本地地址、未指定地址、多播地址及明显保留地址。

**理由**：
- 当前默认兜底列表和上游源中都可能混入明显不应被写入公网 hosts 的地址
- 过滤后可减少无意义检测，并降低误写入 hosts 的风险

**替代方案**：
- 完全信任上游源：风险较高
- 仅过滤解析失败的 IP：力度不足，无法挡住私网/保留地址

### 决策 5：扩展 `status` 以展示 HTTPS/浏览器级验证结果

**选择**：在 `status` 中增加 HTTPS 列和更准确的状态文案；对 `github.com` 的状态优先依据浏览器导向验证输出“正常/部分/失败”。

**理由**：
- 当前用户最容易困惑的是“IP 与 hosts 一致，但浏览器打不开”
- 明确展示 HTTPS/浏览器校验结果，能显著提升可诊断性

**替代方案**：
- 继续只显示端口：信息不足，无法解释浏览器失败原因

## Risks / Trade-offs

- **响应特征可能随 GitHub 页面改版而变化**：通过选择较稳定、宽松的关键标识并允许多组特征匹配来降低脆弱性
- **候选池扩大后全量检测时间上升**：通过只对 `github.com` 做更重校验、对其他域名保持轻量检测来控制耗时
- **过滤规则过严可能错杀少数有效 IP**：优先只拦截明确不应使用的地址类型，避免引入激进的 ASN/CDN 白名单判断
- **CLI 输出列增多影响可读性**：保持列数克制，只增加与用户诊断强相关的信息

## Migration Plan

1. 先修改 OpenSpec 规格，明确浏览器导向验证与 CLI 输出要求
2. 实现候选 IP 聚合与合法性过滤
3. 实现 `github.com` 首页响应特征校验，并接入评分/可用性选择
4. 更新 `status`/`init`/`update` 输出
5. 增加单元测试，并结合 `curl`/`wget` 做手动回归验证
6. 若新策略导致候选明显减少或误判，可回退到仅保留合法性过滤和多源聚合，保留旧版基础 HTTPS 成功判定

## Open Questions

- GitHub 首页最稳定的响应特征应选择哪些字符串，才能兼顾稳健与低误判？
- 是否需要在后续迭代中补充 `github.githubassets.com` 等浏览器关键资源域名的专项验活，而不仅依赖通用 HTTPS 校验？
- 多数据源聚合是否需要进一步改为并发抓取，以减少首次检测总耗时？
